# Removal Map — scaffolding vs. product

> A companion to [DEV_JOURNEY.md](DEV_JOURNEY.md). Some files are *product* — they
> ship and must be maintained. Others were only ever **scaffolding**: reasonable
> *while* you were building something, dead weight once it's built. This file
> separates the two so the repo stays as light as the product actually is.

## The principle

Ask of every file: **does the product need this, or did the *act of building it*
need this?**

- **Product** — the library (`pump/`), the workbench (`pumpflow/`), the spec
  (`UI_SPEC.md`), the decisions (`docs/adr/`, `docs/sprints/`, `docs/product/`),
  the canonical reference notebook, and a *small* set of bundled examples. Keep.
- **Scaffolding** — study material you vendored to learn from, smoke notebooks
  you ran once to check a setup, build artifacts, generated outputs, and
  divergent scratch copies. Remove once their job is done.

Nothing in the removal tiers has been deleted — this is the map. Act on a row
when you're ready, ideally folding it into the sprint it belongs to.

## Two kinds of weight — the hygiene lesson

Before acting on anything below, internalize the distinction that drives all of
it. A repo accumulates two very different kinds of "extra" files, and they call
for **opposite reflexes**:

- **Tracked weight** — files committed to git. *Everyone who clones pays for
  them, forever*, in every checkout and every `git clone`. This is the weight
  worth hunting: vendored study material, divergent copies, generated outputs
  that slipped into a commit. Removing these is a **real task** — it changes the
  repo for every future reader, and (for large files) lives in history until
  rewritten.
- **Local-disk artifacts** — git-ignored build output and caches. They never
  entered version control, so they cost *no one but you*, and one command brings
  them back. Deleting these is **not a removal task — it's routine hygiene**,
  like wiping `node_modules`. Counting them as "reclaimed repo weight" is a
  category error: it frees your disk, not the repo.

The rule that prevents the mess in the first place:

> **Commit sources, never derivatives.** If a file is regenerated by a command
> (`build`, `pytest`, `sphinx-build`, *running a notebook*), it does not belong
> in git — it belongs in `.gitignore`.

The tracked `.docx` reports in Tier 4 are exactly this rule being broken: a
derivative that slipped into version control. The fix is always the same — ignore
the pattern, `git rm --cached` the file, regenerate on demand.

## Bottom line

Keep the two kinds of weight separate (see the hygiene lesson above):

- **Repo weight removed (tracked — everyone's clone):** ~**120 MB**, almost
  entirely `sample_repo` (Tier 1). A clean win with zero product risk — do it in
  one tidy "repo hygiene" commit.
- **Local disk freed (git-ignored — only yours):** ~**10 MB** of regenerable
  artifacts, mostly `docs/_build`. Routine cleanup, *not* a repo saving — don't
  let it inflate the headline.

Tier 2 isn't a deletion but a **consolidation** — one utilities notebook homed in
the gallery as the **UC-00** example (the foundational "use case zero", now
registered in [use-cases.md](product/use-cases.md)); the only open call is which
demo role `tests/` keeps. Tiers 3–4 are quick judgment calls; Tier 4 is now more urgent since all 8 report
`.docx` ended up tracked. Tier 5 is **done** — the `Point` class is already gone;
only the doc references to it need cleanup.
